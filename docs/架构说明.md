# 架构说明

> 本文档说明系统的模块划分、关键数据流与扩展点，对应代码位于 `backend/app/` 与 `frontend/src/`。

## 1. 分层与职责

后端严格采用 **Router / Service / Repository** 三层 + 独立能力层（llm / rag / graph）：

| 层 | 目录 | 职责 | 约束 |
| --- | --- | --- | --- |
| 路由层 | `app/api/**` | 参数校验（Pydantic）、鉴权、调用 Service、返回统一响应 | **不写业务逻辑、不直接操作数据库、不创建模型实例** |
| 服务层 | `app/services/**` | 业务编排、事务边界、缓存、跨仓储协作 | 不直接依赖 FastAPI |
| 仓储层 | `app/repositories/**` | SQLAlchemy 2.x async ORM 查询 | 不写业务判断 |
| 模型层 | `app/models/**` | ORM 表结构、枚举、少量领域方法（`to_dict` / `render`） | 与传输结构解耦 |
| 传输层 | `app/schemas/**` | 出入参 Schema（与前端 `src/types` 一一对应） | API Key 只写不读 |
| 能力层 | `app/llm`、`app/rag`、`app/skills`、`app/mcp`、`app/graph` | 模型工厂、RAG、技能（工具）、MCP 客户端、工作流 | **不依赖 API 层**，可被 Service 与后台任务复用 |
| 基础设施 | `app/core`、`app/db` | 配置、安全、日志、异常、中间件、引擎会话 | 全局单例 |

对应关系举例（一次聊天请求）：

```
app/api/chat.py::chat_stream      （路由：鉴权 + 参数校验 + SSE 响应）
  └─ app/services/chat_service.py （业务：会话/上下文/落库/用量统计）
       ├─ app/graph/workflow.py   （工作流：route → retrieve → generate → finalize）
       │    ├─ app/graph/nodes.py       （节点实现）
       │    └─ app/rag/retriever.py     （检索：向量 + ReRank）
       │         └─ app/rag/vector_store.py（向量库抽象）
       └─ app/llm/factory.py      （统一创建 LLM）
```

## 2. 关键数据流

### 2.1 流式聊天（SSE）

```
前端 fetch(/api/chat/stream, POST, Bearer)
  ↓
ChatService.prepare()
  ├─ 解析 / 创建会话，保存用户消息
  ├─ 解析模型（会话级 model_id → 默认模型）
  ├─ 解析知识库 / Prompt / 会话参数
  ├─ 构造上下文（System + 历史消息 + 当前问题，按条数与字符预算裁剪）
  └─ 预创建助手消息（status=streaming）→ 返回 message_id
  ↓
StreamingResponse(text/event-stream)
  ├─ data: {"type":"start"}
  ├─ data: {"type":"meta", conversation, user_message, assistant_message, model, knowledge_base}
  ├─ data: {"type":"route", use_rag}
  ├─ data: {"type":"sources", sources:[...]}      ← RAG 命中时
  ├─ data: {"type":"token", content:"…"} …        ← 逐字返回
  └─ data: {"type":"done", message, usage, sources, conversation}
  ↓
前端 streamChat()：fetch + ReadableStream 手工解析 SSE 帧
  └─ token 直接追加到响应式助手消息对象（不重建数组）
```

**事件类型**：`start` `meta` `route` `sources` `skill`（技能与 MCP 工具共用，带 `source`）`token` `notice` `error` `done`

### 2.2 停止生成 / 客户端断开

这是流式系统里最容易出错的地方，本项目的处理方式：

1. 生成任务由 `stream_graph()` 启动为后台 `asyncio.Task`，token 经 `asyncio.Queue` 推给响应协程；
2. 连接断开或用户点击停止 → 生成器被关闭 → `finally` 中 `task.cancel()`，**取消底层 LLM 调用**（不再消耗额度），且**不做任何 yield**（否则破坏生成器协议）；
3. 已生成内容由 `schedule_stopped_persist()` **投递到一个全新任务 + 全新数据库会话**中落库，状态标记为 `stopped`；
   - 原因：响应协程此时正在被销毁，其中的任何 `await`（含数据库写入）都会被取消并回滚，消息状态将永远停留在 `streaming`；
   - 独立任务不受响应生命周期影响，保证「停止后仍保留已生成内容」。

### 2.3 RAG 入库流水线

```
UploadFile → 类型/大小/文件名校验 → 随机存储名落盘 → SHA256 去重
   ↓（后台任务，进度写回 documents.progress）
Document Loader（pdf/docx/txt/md/csv/xlsx）→ 文本清洗 → Text Splitter
   ↓
Embedding（分批，进度 40%→90%）→ Vector Store.add_chunks
   ↓
更新 documents（completed/failed、chunk_count、char_count）→ 重算知识库统计
```

### 2.4 RAG 检索

```
question → Query Embedding → VectorStore.similarity_search
   → 阈值过滤 → （可选 ReRank：0.65 * 向量相似度 + 0.35 * 词法重合度）
   → 去重 → Top K → build_context（带 [1][2] 编号 + 文件名 + 页码）
   → 注入 System Prompt（{context} 占位或追加【知识库内容】块）
   → LLM → Answer + sources
```

### 2.5 技能（Skills）与 Tool Calling

```
技能配置（管理后台）                             聊天请求（skill_ids）
   skills 表：type / config / enabled                 
                                                     v
        v                               SkillService.resolve_for_chat()
  app/skills/registry.py                     （过滤：已禁用 / 未配置 / 不允许用户使用）
    validate_config()                     v
    create_skill()  > BaseSkill 子类  registry.build_tools()
    build_tools()   > LangChain Tool（name / description / args_schema）
                                                  
                                                  v
                                     LangGraph：generate <> tools
```

关键点：

1. **技能类型 = 代码，技能实例 = 数据**：`calculator` 是类型（代码实现一次）；管理员可基于
   `http_request` 类型创建任意多个实例（订单接口、天气接口）。
2. **动态表单**：前端不写死任何配置项，完全由 `SkillSpec.fields` 驱动
   （string / password / text / json / number / integer / boolean / select）；工具入参由
   `SkillSpec.args`（或自定义技能的 `config.args_schema`）转成 pydantic 模型，作为 Tool 的 `args_schema`。
3. **安全**：`password` / `secret` 字段出参脱敏（`mask_secret`），更新时留空表示保持原值；
   计算器用 `ast` 白名单求值（拒绝 `__import__` 等）；网页抓取默认拒绝内网地址（SSRF 防护）。
4. **执行闭环**（`app/graph/nodes.py`）：
   - `generate` 用 `astream` 边流式输出边累积完整消息；若含 `tool_calls`，本轮只推事件、不产出正文，转入 `tools`；
   - `tools` 节点执行工具  推送 `skill/call`、`skill/result` 事件  把**规范化的 `AIMessage`**
     （显式带 `tool_calls`）与 `ToolMessage` 追加进消息列表  回到 `generate` 生成最终回答；
   - 最多 `max_tool_rounds`（默认 4）轮，防止模型反复调用导致死循环。
   > 细节：流式累积出来的是 `AIMessageChunk`，直接回喂 OpenAI 兼容接口会报
   > 「Messages with role 'tool' must be a response to a preceding message with 'tool_calls'」，
   > 必须重建 `AIMessage`。
5. **落库**：`messages.skills` 保存调用明细（名称 / 入参 / 结果 / 耗时 / 状态），
   `conversations.skill_ids` 保存会话级选择，`skills.usage_count` 累计调用次数。
6. **降级**：模型不支持 `bind_tools` 时自动忽略已选技能并向前端提示，不影响普通对话。

### 2.6 MCP（Model Context Protocol）

MCP 服务通过「连接时发现工具 + 缓存 JSON Schema」的方式接入，聊天时与本地技能
**共用同一套 tool-calling 链路**（`generate  tools`），因此不需要任何额外的编排逻辑：

```
MCP Server（stdio / sse / http）
       tools/list（点「测试连接」时拉取）
     v
mcp_servers.tools_cache（JSON Schema 缓存）
     
     v
app/mcp/bridge.py  json_schema_to_model()  StructuredTool
     
     v
ChatService.prepare()：tools = 技能工具 + MCP 工具（skill_meta 里带 source/server）
     
     v
LangGraph generate  tools（事件里带 source=mcp / server=服务名）
```

关键点：

1. **协议细节收敛在 `app/mcp/client.py`**：三种传输（`stdio_client` / `sse_client` /
   `streamable_http_client`）的差异、以及 mcp SDK 1.x  2.x 的 API 变更（`streamablehttp_client`
    `streamable_http_client`、`inputSchema`  `input_schema`）都在这一层做兼容，上层无感。
2. **每次操作建立一次连接**：实现简单、不泄漏子进程、并发安全；代价是每次调用有一次握手
   （本地 stdio 约 0.8s）。如需长连接，只需在这一层加连接池。
3. **schema 缓存**：`tools_cache` 存 MCP 工具的 JSON Schema，聊天时直接构建 LangChain Tool，
   避免每次请求都握手；服务端工具变更后点「测试连接」刷新。
4. **工具命名**：`mcp_<server_slug>_<tool_name>`（清洗为 OpenAI 允许的字符集），
   slug 为纯中文时退化为 `srv<短哈希>`。
5. **安全**：`env` / `headers` 的敏感值加密存储、出参脱敏、编辑留空不覆盖；
   连接失败只回可读原因（命令不存在 / 连接被拒 / 超时 / 401 / 404）。
6. **降级**：模型不支持 Function Calling 时忽略已选 MCP 服务并提示，不影响普通对话。

## 3. LangGraph 工作流

```python
class ChatState(TypedDict, total=False):
    messages: list[BaseMessage]     question: str
    context: list[dict]             context_text: str
    knowledge_base_id: int | None    knowledge_base_name: str | None
    model_id: int | None             model_name: str | None
    system_prompt: str               use_rag: bool          route: str
    answer: str                      sources: list[dict]    usage: dict
    retrieval_failed: bool           error: str | None      notices: list[str]
```

```
START
  │
  → route（判断是否使用知识库）
    ├── 是 → retrieve（RAG 检索）──→ generate
    └── 否 ───────────────────→ generate
                                          │
                        ┌── 模型返回 tool_calls ──→ tools（执行技能）
                        └── 无 tool_calls ────────→ finalize → END

（tools 执行完成后回到 generate，最多 max_tool_rounds=4 轮）
```

- 节点通过闭包持有 `ChatDeps`（llm / retriever / 事件队列 / 当前问题），因此工作流完全不感知 HTTP；
- 检索失败或未命中时**降级为普通对话**，并向前端推送 `notice`；
- 扩展方向：在 `nodes.py` 增加 `intent`（意图识别）、`agent` 等节点并在 `workflow.py` 中加边；技能（Tool Calling）已实现为 `generate  tools` 循环。

## 4. 数据库设计

### 4.1 数据存放位置（本项目所有业务数据均在关系库中）

| 数据 | 表 / 列 | 说明 |
| --- | --- | --- |
| 对话记忆 | `conversations` / `messages` | 多轮上下文；`messages.sources`(JSON) 存该条回答的引用；`conversations.summary` 存超长上下文摘要 |
| 知识库 | `knowledge_bases` | Embedding / Chunk / Retriever 全部配置 |
| 文档元数据 | `documents` | 状态机、进度、分块数、SHA256、解析元数据 |
| 文档正文 | `document_chunks.content` | 切分后的 Chunk 文本，RAG 只依赖它，不依赖磁盘原文件 |
| **向量库** | `document_chunks.embedding` | float32 二进制（LONGBLOB / BLOB），内置向量库实现即以此表为存储 |
| 模型与密钥 | `models` | `api_key` 为 Fernet 密文 |
| Prompt | `prompts` | 内置 + 自定义 |
| 调用统计 | `usage_logs` | Dashboard 数据源 |

> 原始上传文件保存在磁盘 `backend/storage/uploads/`（仅用于「重新向量化」与回溯）。
> 若确需连原文件也入库，可参照 `app/models/document.py` 增加 `file_blob` 列并在
> `document_service.upload_document()` 中写入（注意 MySQL `max_allowed_packet` 与本机磁盘/备份策略）。

### 4.3 跨数据库注意事项（SQLite ↔ MySQL 均已实测）

1. **类型映射**：主键 `BigInteger().with_variant(Integer, "sqlite")` → MySQL `BIGINT AUTO_INCREMENT`、SQLite `INTEGER PRIMARY KEY`；
   大文本用 `LongText = Text().with_variant(MEDIUMTEXT, "mysql")`，避免 MySQL `TEXT` 64KB 限制在 `STRICT_TRANS_TABLES` 下报错；
   向量列 `LargeBinary(2**24)` → MySQL `LONGBLOB`（8192 维仅 32KB，余量充足）、SQLite `BLOB`。
2. **`updated_at` 必须用 Python 端 `onupdate`**：纯服务端 `func.now()` 会让属性在 UPDATE 后变成 expired，
   异步上下文再访问会抛 `MissingGreenlet`。
3. **连接池**：SQLite 用 `NullPool` 且关闭 `pool_pre_ping`（规避文件锁与 aiosqlite 的 `MissingGreenlet`）；
   MySQL 用 `pool_pre_ping + pool_recycle`。
4. **`ONLY_FULL_GROUP_BY`**：统计查询全部显式 `GROUP BY`，在 MySQL 8 默认 sql_mode 下验证通过。
5. **表结构管理**：MySQL 环境设 `AUTO_CREATE_TABLES=false`，统一 `alembic upgrade head`；
   应用启动时 `check_schema_ready()` 会自检缺表并给出修复提示。

## 5. 安全设计

| 风险 | 处理 |
| --- | --- |
| API Key 泄露 | Fernet 加密存储；接口只返回脱敏值；日志过滤器自动脱敏 `sk-*` / `Authorization` / `password` |
| XSS | Markdown 全部经 DOMPurify 清洗；代码块复制按钮用 DOM API 注入（避免内联脚本） |
| SQL 注入 | 全部使用 SQLAlchemy ORM / 参数绑定，无字符串拼接 SQL |
| 越权访问 | 仓储层 `get_owned()` 强制带 `user_id` 条件；管理员接口 `Depends(get_current_admin)` |
| 文件上传 | 扩展名白名单 + 大小限制 + 文件名清洗 + 随机存储名 + 非执行目录；错误信息脱敏（隐藏服务器路径） |
| 信息泄露 | 统一异常处理，生产环境不返回 traceback / SQL / 路径 / 内部系统信息 |
| 登录态 | JWT（HS256）+ 过期时间；密码 PBKDF2-HMAC-SHA256（26 万次迭代，兼容校验历史 bcrypt 哈希） |

## 6. 可观测性

- 日志格式：`时间 | 级别 | 模块 | rid=请求ID uid=用户ID | 内容`，支持控制台 + `logs/app.log`（轮转）+ `logs/error.log`
- 请求 ID 通过 `X-Request-ID` 响应头回传，便于前后端联调定位
- `usage_logs` 记录每次调用的 provider / model / tokens / 检索片段数 / 耗时 / 成功率，Dashboard 基于它聚合

## 7. 前端结构约定

- **状态管理**：`stores/user`（登录态）、`stores/settings`（会话参数与 UI 偏好，持久化 localStorage）、`stores/model`、`stores/knowledge`、`stores/chat`（会话与流式消息）
- **API 层**：`api/request.ts` 统一拦截器（注入 Token、拆包 `code/data`、401 跳登录、统一错误提示）；`utils/sse.ts` 负责流式解析
- **组件分层**：基础 UI 一律用 Ant Design Vue；业务组件自研（`ChatMessage` / `ChatInput` / `ChatHeader` / `ConversationList` / `ModelSelector` / `KnowledgeSelector` / `PromptSelector` / `RagSource` / `MarkdownRenderer` / `CodeBlock` / `ModelConfigForm` / `KnowledgeCard` / `KnowledgeConfigForm` / `DocumentList`）
- **布局**：页面以 `<ChatLayout>` / `<AdminLayout>` 包裹（布局内使用 `<slot />` 而非嵌套 `router-view`，避免路由视图递归）
- **状态覆盖**：所有列表都有 Loading / Empty / Error 三态，流式回答有「AI 正在思考…」与光标动画
